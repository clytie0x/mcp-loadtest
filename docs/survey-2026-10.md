# MCP servers that keep state: a concurrency survey (October 2026)

On 2026-10-20 we ran mcp-loadtest against 37 published MCP servers that keep
state in a file, a local database or process memory. We looked for two
things: writes that a server acknowledges and then loses, and tool calls
that hang while other calls are in flight.

## Results

| | Servers |
|---|---|
| Tested | 37 (26 npm, 11 PyPI) |
| Lose acknowledged writes | 6 |
| ... inside one process, when a client sends tool calls in parallel | 4 |
| ... only when several processes share one store | 2 |
| Deadlock or hang | 0 |
| Fail some parallel writes with an internal error, without losing any | 1 |
| Fail some calls when several processes start on an empty store | 3 (a fourth once, not reproduced) |

The six servers that lose writes:

| Server | Version | Downloads/wk | What is lost | Lost (pipelined runs) | Lost (5 processes) |
|---|---|---|---|---|---|
| `@wonderwhy-er/desktop-commander` | 0.3.0 | 195,946 | `edit_block` edits to one file | 12, 12, 12 of 15 | 0 of 15 |
| `@itseasy21/mcp-knowledge-graph` | 1.0.7 | 916 | Entities from `create_entities`; with 5 processes the store file was left torn and unreadable | 12, 12, 12 of 15 | incomplete: file torn |
| `compound-memory` | 0.5.9 | 686 | Search-index entries for notes that are on disk | 0 | 8 of 15, twice |
| `notes-vault-mcp` | 0.7.0 | 156 | `append_file` appends to one note | 7 of 13, 1 of 10, 0 of 8 | 5 of 13 |
| `brain-os` | 0.10.0 | 60 | Decisions from `decision_log` | 12, 12, 12 of 15 | 5 of 15 |
| `mcp-simple-memory` | 0.4.0 | 8 | Memories from `mem_save` | 0 | 12 of 15 in 3 of 3 script runs |

Every lost write was acknowledged: the tool call returned success. Each
count was checked against the store on disk, and each write path was read
in the published package. Downloads are npm weekly or pypistats last-week
counts on 2026-10-20.

In the pipelined runs, one write of each round of 5 survived, the same
1-of-N pattern as earlier findings. notes-vault-mcp also refused between 2
and 7 appends per run with a false validation error (`would not be a valid
note`), because it read the note while another call was rewriting it.

## The common cause

Five of the six read the whole store, change it in memory, and write it
back, with no lock and an `await` (or a worker thread) between the read and
the write. Whichever call writes last wins.

- desktop-commander reads the file in `performSearchReplace`
  (`dist/tools/edit.js:110`) and writes the new content at `:160`.
- `@itseasy21/mcp-knowledge-graph` calls `loadGraph` (`fs.readFile`,
  `dist/index.js:24`) and `saveGraph` (`fs.writeFile`, `:44`). This is the
  pattern the reference memory server removed in 1.0.0 with a lock file.
  Because `fs.writeFile` truncates first, two processes writing at once
  left half a line in the file, and every later call failed to parse it.
- brain-os reads all decisions and rewrites `decisions.json`
  (`dist/tools/decision-log.js:45-46` and `:80`). The package notes the
  race itself in `dist/utils/file-store.js:123`.
- notes-vault-mcp's `append` (`notes.py:115`) writes without the version
  check that its `write_file` uses, through an in-place `write_bytes`
  (`backends/local.py:98`).
- mcp-simple-memory loads its SQLite database into memory once at start-up
  (`dist/index.js:36-39`) and saves the whole copy on every write (`:91-92`),
  so each process overwrites the others.

compound-memory is the exception: every note is written to its own file
under a cross-process lock, but the write path updates a search index held
in memory without reloading it when another process has changed it
(`index.py:269`), so the index file ends up with one process's view.

The servers that passed used SQLite transactions, one file per record, a
lock file, or a version check. Six SQLite servers answered some of the
5-process writes with `database is locked` and kept every acknowledged write.
That is safe, but a client without retries sees those calls fail.

## Method

- Candidates came from the official MCP Registry (every stdio npm and PyPI
  package in the latest-version listing) and npm search, filtered to
  servers that store something and run locally without an account or API
  key, then ranked by downloads. 37 were tested. 36 other candidates were
  skipped, each with its reason in
  [field-results.md](field-results.md#skipped), as were 11 servers already
  tested in earlier runs.
- Each server ran from a pinned package version against a fresh scratch
  store. A write tool and a read tool were picked by hand from its tool
  list. Each write stored a unique marker, and the read had to return every
  acknowledged marker.
- `lost-update --pipelined --concurrent 5 --writes-per-worker 3`, 3 runs:
  one server process, 3 rounds of 5 writes sent without waiting for
  replies, as a client that runs tool calls in parallel does.
- `lost-update --concurrent 5 --writes-per-worker 3`, 1 run: 5 server
  processes on one store, as with several agents or editor windows.
- `deadlock-probe --concurrent 5`, 1 run on the read tool: 5 processes
  call it at the same moment.
- mcp-loadtest `v0.6.0`, Linux, Node 22.22.0, Python 3.13 and 3.14.

## Limits

- 37 servers is a small sample, skewed toward memory and task servers, and
  most of them have few downloads. Only one, desktop-commander, has more
  than 25,000 weekly downloads.
- 15 writes per run finds wide race windows. A pass means no write was lost
  in these runs, not that the server is race-free. One notes-vault-mcp run
  passed although the other runs lost writes.
- One write tool was tested per server. A server that passes for one tool
  can lose writes in another, as mnemonic-mcp did on 2026-10-19.
- Two servers allow one process per store by design (a DuckDB file lock and
  a fixed web port), so only their one-process result counts. One server's
  5-process run was inconclusive because loading a language model in 5
  processes at once exceeded the hang threshold.
- Upstream `main` was not checked; the counts are for the versions listed.
- No finding has been reported to its maintainers yet.
- The check missed one loss: for mcp-simple-memory, mcp-loadtest reported
  the 5-process run as inconclusive, and a script found the loss. That gap
  is recorded as a tool defect.
